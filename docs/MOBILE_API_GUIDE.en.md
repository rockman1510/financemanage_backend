# API guide for the mobile app (KMP – Android & iOS)

> Vietnamese version: [MOBILE_API_GUIDE.md](MOBILE_API_GUIDE.md). Both versions use the same section numbers, so
> "API §n" points to the same content in either file.

This document is for the people (and Claude Code) building the **Kotlin Multiplatform** app that calls the Finance
Manage backend. It explains *how to use* the API: the authentication flow, conventions, how to handle money and
asynchronous states, every feature, and the error codes.

- **Machine-readable spec**: [`docs/api/openapi.json`](api/openapi.json) (OpenAPI 3, 119 endpoints, generated by the
  backend itself). While the backend runs: `GET /v3/api-docs`, UI at `GET /swagger-ui.html` (off by default in
  production).
- **Manual call examples per flow**: [`docs/API_TEST_GUIDE.md`](API_TEST_GUIDE.md) (Vietnamese); script running every
  flow: `scripts/api-flow-test.sh`.
- **Feature scope**: [`docs/FEATURE_SCOPE.md`](FEATURE_SCOPE.md) (Vietnamese).

> Every sample JSON below was captured from the real backend (`dev` profile). Data values such as category names and
> notification texts are in Vietnamese, because the backend serves Vietnamese users. When this document and
> `openapi.json` disagree on a field name, trust `openapi.json`; when they disagree on a business rule, trust this
> document and `API_TEST_GUIDE.md`.

## 1. Environments and running the backend

| Environment | Base URL | Notes |
|---|---|---|
| Local, without Docker | `http://localhost:8080` | `cd backend && ./gradlew :app:bootRun --args='--spring.profiles.active=dev'` (H2, fake mailbox) |
| Local, Docker | `http://localhost:8080` | `docker compose up --build` in the repository root (PostgreSQL) |
| Android emulator → host machine | `http://10.0.2.2:8080` | The iOS simulator can use `http://localhost:8080` |
| Real device on the LAN | `http://<machine IP>:8080` | Android needs cleartext allowed for debug; iOS needs an ATS exception for debug |
| Production | `https://<DOMAIN>` | See [DEPLOYMENT.md](DEPLOYMENT.md) |

Every business endpoint lives under **`/api/v1`**. Liveness check: `GET /actuator/health` → `{"status":"UP"}`
(local only; production does not expose actuator).

The **`dev` profile** adds `GET /api/v1/dev/mailbox?to=<email>` (no token needed), which returns the e-mails "sent" –
use it to read e-mail verification and password reset codes while developing the app. This endpoint **does not exist**
in production.

## 2. General conventions

| Topic | Convention |
|---|---|
| Format | UTF-8 JSON, `Content-Type: application/json`. camelCase field names. Fields without a value are returned as `null` (not omitted) |
| Authentication | `Authorization: Bearer <accessToken>` on every endpoint except `/auth/*` |
| IDs | UUIDs as strings |
| Dates | `LocalDate` ISO `yyyy-MM-dd` (e.g. `2026-11-01`); when the backend defaults to "today" it uses **Vietnam time** (`Asia/Ho_Chi_Minh`) |
| Instants | `Instant` ISO-8601 UTC, e.g. `2026-11-01T10:15:07.978238Z` (the number of fractional digits varies) |
| Time of day | `HH:mm[:ss]` (notification settings) |
| **Money** | JSON numbers (`45000`, `40.00`, `94.67`) that are **exact decimals** – never use `Double`/`Float` (see section 15). Rounded to the currency's minor unit: VND 0 decimals, USD 2. Sending more decimals than the currency allows → `422 INVALID_AMOUNT` |
| Currencies | 3-letter upper-case ISO 4217 codes (`VND`, `USD`). Default `VND` when omitted |
| Percentages | Numbers, e.g. `6` = 6% per year; `percent` in responses is 0–100 (may exceed 100 when over) |
| Pagination | Only `GET /transactions`: `page` (from 0), `size` (default 20, max 100) → `{items, page, size, totalElements, totalPages}`. Other lists return the full array |
| Updates | `PATCH` is a **partial** update: omitted / `null` fields stay unchanged. Clearing a value uses a dedicated flag (e.g. `clearDeadline: true`) |
| Success codes | `200` read/update, `201` created, `202` accepted for asynchronous processing, `204` no content |
| Idempotency | `Idempotency-Key` header (string ≤ 100 characters, a UUID is recommended) for `POST /transactions`, `POST /transfers`, `POST /loans/{id}/repayments`, `POST /loans/{id}/prepayments`. Sending the same key again returns the first result and **records nothing twice**. Use the same key for every retry of the *same* action (lost network, timeout) |
| Authorisation | Users only see their own data; someone else's id → `404` |

### 2.1 Asynchronous actions (`PENDING` state)

The backend is a modular monolith whose modules talk through events: when a feature needs to **move money in a
wallet** (paying a bill, depositing to / withdrawing from a saving goal, buying/selling an asset, opening/settling a
bank deposit with a wallet), it answers immediately and the ledger records the money a moment later (usually a few
hundred ms). The response carries a status:

```
PENDING ──(the ledger recorded it)──▶ RECORDED  (+ transactionId)
        └─(refused: archived wallet, wrong currency…)──▶ FAILED (+ failureReason)
```

The app should: show a "processing" result right away, then **reload the object** (poll every 1–2 seconds for up to
~10 seconds, or when the user comes back to the screen) until it is no longer `PENDING`; then refresh the wallet
balances. While `PENDING`, editing that same object may return `409 CONCURRENT_MODIFICATION` → retry later.

| Feature | Endpoint | Status field |
|---|---|---|
| Bills | `POST /bills/{id}/pay` (202) | `payments[].status`: `PENDING/RECORDED/FAILED/SKIPPED` |
| Saving goals | `POST /saving-goals/{id}/deposits` / `withdrawals` (202) | `movements[].status` |
| Investments | `POST /investments/{id}/buys` / `sells` / `incomes` (201) | `trades[].cashStatus`: `NONE/PENDING/RECORDED/FAILED` |
| Bank deposits | `POST /deposits` (`fromWalletId`), `POST /deposits/{id}/settle` (`toWalletId`) | `fundingStatus`, `payoutStatus` |

Reports (`/reports/*`) are also updated asynchronously after every transaction (a few hundred ms).

## 3. Errors

Every error has the same shape:

```json
{"code":"VALIDATION_FAILED","message":"Request validation failed",
 "fieldErrors":{"name":"must not be blank","type":"must not be null"},
 "timestamp":"2026-11-01T10:15:07.798400582Z"}
```

| HTTP | When | `code` |
|---|---|---|
| `400` | Wrong type / missing required field (Bean Validation); malformed JSON | `VALIDATION_FAILED` (with `fieldErrors`: field name → message) |
| `401` | Missing/expired access token (empty body); wrong password, invalid refresh token, wrong 2FA code | empty, or `INVALID_CREDENTIALS` |
| `404` | Does not exist or does not belong to the user | `NOT_FOUND` |
| `409` | Concurrent update conflict | `CONCURRENT_MODIFICATION` → reload and retry |
| `422` | Business rule violated | A specific code, see below |
| `429` | Too many attempts | `ACCOUNT_LOCKED` (5 wrong passwords → locked 15 minutes), `RESEND_TOO_SOON` (code resent < 1 minute) |

What the user sees should be based on **`code`** (translated on the app side); `message` is English text for logs.
Common `422` codes by group:

| Group | Codes |
|---|---|
| General | `INVALID_AMOUNT`, `INVALID_CURRENCY`, `CURRENCY_MISMATCH`, `INVALID_NAME`, `INVALID_DATE_RANGE`, `INVALID_PERIOD`, `PERIOD_TOO_LONG`, `NOTE_TOO_LONG`, `FOREIGN_RESOURCE`, `IDEMPOTENCY_KEY_REUSED`, `INVALID_IDEMPOTENCY_KEY` |
| Account | `EMAIL_TAKEN`, `WRONG_PASSWORD`, `INVALID_CODE`, `NO_CODE`, `EMAIL_ALREADY_VERIFIED`, `TWO_FACTOR_ALREADY_ENABLED`, `TWO_FACTOR_NOT_ENABLED`, `TWO_FACTOR_NOT_SET_UP`, `CONFIRMATION_MISMATCH`, `GOOGLE_SIGN_IN_DISABLED`, `INVALID_LOCALE`, `INVALID_TIME_ZONE`, `INVALID_MONTH_START_DAY` |
| Wallets / transactions | `WALLET_ARCHIVED`, `WALLET_HAS_TRANSACTIONS`, `WALLET_REQUIRED`, `INVALID_CREDIT_LIMIT`, `INVALID_DAY_OF_MONTH`, `NOTHING_TO_ADJUST`, `TRANSACTION_NOT_EDITABLE`, `SAME_WALLET`, `TRANSFER_AMOUNT_MISMATCH`, `EXCHANGE_RATE_MISSING`, `SAME_CURRENCY` |
| Categories | `CATEGORY_IN_USE`, `CATEGORY_HAS_CHILDREN`, `CATEGORY_TOO_DEEP`, `CATEGORY_TYPE_MISMATCH`, `INVALID_CATEGORY` |
| Receipt photos | `ATTACHMENT_TYPE_NOT_ALLOWED`, `ATTACHMENT_TOO_LARGE`, `TOO_MANY_ATTACHMENTS` |
| Budgets / bills | `PERIOD_REQUIRED`, `INVALID_END_DATE`, `BILL_FINISHED`, `INVALID_REMIND_DAYS`, `INVALID_INTERVAL`, `PAYMENT_NOT_FOUND` |
| Savings | `INSUFFICIENT_SAVINGS`, `GOAL_NOT_EMPTY`, `ROUND_UP_TAKEN`, `INVALID_ROUND_UP`, `INVALID_AUTO_CONTRIBUTION` |
| Deposits | `DEPOSIT_ALREADY_SETTLED`, `INVALID_SETTLEMENT_DATE`, `INVALID_TERM`, `INVALID_RATE` |
| Loans | `OVERPAYMENT`, `SETTLE_DUE_INSTALLMENTS_FIRST`, `LOAN_NOT_ACTIVE`, `INTEREST_FREE_LOAN`, `INVALID_EFFECTIVE_DATE` |
| Investments | `INSUFFICIENT_QUANTITY`, `FEE_TOO_HIGH`, `STALE_PRICE`, `INVALID_QUANTITY`, `INVALID_PRICE` |
| Notifications | `INVALID_PUSH_TOKEN`, `INVALID_QUIET_HOURS` |

## 4. Authentication and account

### 4.1 Tokens

- **Access token**: JWT HS256, lives **15 minutes** (`expiresInSeconds: 900`). Claims: `sub` (user id), `sid` (session
  id), `email`, `name`. The app does not need to decode it, only to send it in the header.
- **Refresh token**: random string, lives **30 days**, **single use** (rotation): every `POST /auth/refresh` returns a
  new pair and the old token stops working. Reusing an old token → `401` and **the whole session is revoked**
  (theft protection) → the app must sign out to the sign-in screen.
- Every sign-in creates a **session** (device) – listed/revoked under `/me/sessions`. Send `deviceName` when signing in
  or up so that users recognise their devices.

```
POST /api/v1/auth/register  {"email","password","fullName","deviceName"?}        → 201 TokenPair
POST /api/v1/auth/login     {"email","password","deviceName"?}                   → 200 LoginResponse
POST /api/v1/auth/google    {"idToken","deviceName"?}                            → 200 LoginResponse
POST /api/v1/auth/2fa/verify {"challengeToken","code"}                           → 200 TokenPair
POST /api/v1/auth/refresh   {"refreshToken"}                                     → 200 TokenPair
POST /api/v1/auth/logout    {"refreshToken"}                                     → 204 (revokes the session)
POST /api/v1/auth/forgot-password {"email"}                                      → 204 (always 204, never reveals whether the e-mail exists)
POST /api/v1/auth/reset-password  {"email","code","newPassword"}                 → 204 (signs out every device)
```

```json
// TokenPair
{"accessToken":"eyJhbGciOiJIUzI1NiJ9…","refreshToken":"4XBcRuJiTY30RjWSKpZBRqlFck33YbYRBtCIe-0KBF4","expiresInSeconds":900}

// LoginResponse when the account has 2FA enabled: no tokens, call /auth/2fa/verify within 5 minutes
{"accessToken":null,"refreshToken":null,"expiresInSeconds":null,
 "twoFactorRequired":true,"challengeToken":"…","challengeExpiresInSeconds":300}
```

Rules: password 8–72 characters; 5 wrong passwords → `429 ACCOUNT_LOCKED` for 15 minutes; `/auth/2fa/verify` accepts a
6-digit TOTP code **or** a recovery code (single use); after 5 wrong codes the challenge expires.

**Google sign-in**: the app obtains a **Google ID token** (Android: Credential Manager / Google Identity; iOS:
GoogleSignIn SDK) and sends it to `/auth/google`. The backend checks the signature, and `aud` must be listed in
`GOOGLE_CLIENT_IDS` (declare the Android, iOS and web client ids). Unknown e-mail → account created; existing e-mail →
linked. Not configured → `422 GOOGLE_SIGN_IN_DISABLED`.

### 4.2 Profile, e-mail, password, 2FA, sessions, account deletion

| Endpoint | Description |
|---|---|

|---|---|

| `GET/PATCH/DELETE /wallets/{id}` | `PATCH` changes the name, icon, archived flag (`archived`), initial balance, credit card details. **The currency cannot change**. Deletion only without transactions (`WALLET_HAS_TRANSACTIONS`) – otherwise archive it |

### 5.3 Income and expense transactions

| Endpoint | Description |
|---|---|
| `POST /transactions` (+ `Idempotency-Key`) | `{walletId*, categoryId*, amount*, occurredOn?, note?, withPerson?, excludeFromReport?}` – the type (income/expense) follows the category; `amount` > 0; `occurredOn` defaults to today; `note` ≤ 500, `withPerson` ≤ 120 characters |
| `GET /transactions?walletId&categoryId&type&from&to&minAmount&maxAmount&q&page&size` | Newest first. `categoryId` and `type` can repeat (`?type=INCOME&type=EXPENSE`); a parent category filter includes its children; `q` searches the note and person |
| `GET /transactions/summary?…` (same filters, no paging) | `[{currency, income, expense, net}]`, one row per currency – transfers, adjustments, `EXTERNAL_*` and `excludeFromReport` transactions are **not** counted |
| `GET/PATCH/DELETE /transactions/{id}` | Only income/expense entered by the user can be edited/deleted (`TRANSACTION_NOT_EDITABLE` for transfers, adjustments and transactions created by other modules). Edits/deletions update the wallet balance |

Transaction `type`: `INCOME`, `EXPENSE`, `TRANSFER_IN/OUT` (between wallets), `ADJUSTMENT_IN/OUT` (balance adjustment),
`EXTERNAL_IN/OUT` (money to/from saving goals, investments, bank deposits – **not income/expense**). Transactions
created by other modules carry a `source` (`BILL`, `SAVING`, `INVESTMENT`, `DEPOSIT_OPEN`, `DEPOSIT_SETTLE`) and a
`sourceId`.

```json
{"id":"90ddef81-3da6-4529-b7c5-9858e6842e04","walletId":"1e1a4d7a-…","type":"EXPENSE","amount":45000,"currency":"VND",
 "categoryId":"da49d9f1-…","occurredOn":"2026-11-01","note":"Phở","withPerson":null,"excludeFromReport":false,
 "transferId":null,"counterpartWalletId":null,"exchangeRate":null,"recurringId":null,"source":null,"sourceId":null,
 "createdAt":"2026-11-01T10:15:07.978238165Z","attachments":null}
```

### 5.4 Transfers between wallets

`POST /transfers` (+ `Idempotency-Key`) `{fromWalletId*, toWalletId*, amount*, receivedAmount?, occurredOn?, note?}` →
`201 {transferId, out, in}` (2 transactions `TRANSFER_OUT` / `TRANSFER_IN`). Different currencies: send
`receivedAmount` (the amount actually received) **or** leave it out to use the user's exchange rate (section 6); no
rate → `EXCHANGE_RATE_MISSING`. `DELETE /transfers/{transferId}` deletes both sides.

### 5.5 Recurring transactions

`POST /recurring-transactions` `{walletId*, categoryId*, amount*, note?, withPerson?, frequency*, interval?, startDate*,
endDate?}` – `frequency`: `DAILY`, `WEEKLY`, `MONTHLY`, `YEARLY`; `interval` defaults to 1 (2 = every 2 months…). A
daily job records the due occurrences (dates do not drift: 31 Jan → 28 Feb → 31 Mar). The response has
`nextOccurrence`, `generatedCount`, `active`. `PATCH` changes the wallet, category, amount, note, `endDate`, pause
(`active:false`). `GET`, `GET /{id}`, `DELETE /{id}`.

### 5.6 Receipt photos

- `POST /transactions/{transactionId}/attachments` – **multipart/form-data**, part named **`file`**; JPEG, PNG, WebP,
  HEIC or PDF; ≤ 5 MB; at most 5 files per transaction → `201 {id, fileName, contentType, size, createdAt}`.
- `GET /attachments/{id}` – downloads the content (binary body, original `Content-Type`; needs the `Authorization`
  header, so download with Ktor and display it rather than giving the URL to an image library that does not send the
  header).
- `DELETE /attachments/{id}`.

## 6. Multiple currencies

| Endpoint | Description |
|---|---|
| `GET /exchange-rates?base&quote` | Rates entered by the user + global rates (`global:true`, when an automatic source exists) |
| `POST /exchange-rates` `{base*, quote*, rate*, effectiveDate?}` | 1 `base` = `rate` `quote`, e.g. `USD`→`VND` 25000. The same pair + date overwrites |
| `DELETE /exchange-rates/{id}` | |
| `GET /exchange-rates/convert?amount&from&to&date` | `{amount, from, to, rate, converted, date}` |

Rate selection: the user's rates win over global rates; the latest rate effective **on or before** the needed date is

## 7. Budgets

| Endpoint | Description |
|---|---|
| `POST /budgets` | `{name*, amount*, currency?, categoryIds?, walletId?, period*, startDate?, endDate?, repeat?}` |
| `GET /budgets?date=` / `GET /budgets/{id}?date=` | Includes `current`: the status of the period containing `date` (default today) |
| `PATCH /budgets/{id}` | `{name?, amount?, categoryIds?, walletId?, allWallets?, repeat?}` – `allWallets:true` removes the wallet limit |
| `DELETE /budgets/{id}` | |

- `period`: `WEEKLY` (starts on Monday), `MONTHLY`, `QUARTERLY`, `YEARLY`, `CUSTOM` (needs `startDate`, `endDate`).

- `state`: `NOT_STARTED`, `ON_TRACK`, `WARNING` (≥ 80%), `EXCEEDED` (≥ 100%), `ENDED`. `dailySuggestion` = remaining /

```json

 "period":"MONTHLY","startDate":"2026-11-01","endDate":null,"repeat":true,
 "current":{"periodStart":"2026-11-01","periodEnd":"2026-11-30","spent":45000,"remaining":2955000,"percent":1,
            "dailySuggestion":98500,"daysLeft":30,"state":"ON_TRACK","unconvertedCurrencies":[]}}
```

## 8. Recurring bills

| Endpoint | Description |
|---|---|
| `POST /bills` | `{name*, amount*, walletId*, categoryId*, frequency*, interval?, firstDueDate*, endDate?, remindDaysBefore?, note?}` – `frequency`: `WEEKLY`, `MONTHLY`, `QUARTERLY`, `YEARLY`; `categoryId` is an **expense** category; the currency is the wallet's |
| `GET /bills`, `GET /bills/{id}` | With `nextDueDate`, `daysUntilDue`, `overdue`, `active`, `payments` (newest first) |
| `GET /bills/upcoming?days=30` | Bills due within N days (overdue ones included) |
| `PATCH /bills/{id}` | `{name?, amount?, walletId?, categoryId?, endDate?, remindDaysBefore?, note?, active?}` (`active:false` = paused) |
| `POST /bills/{id}/pay` `{amount?, walletId?, paidOn?}` | **202**, pays the period currently due: records an expense through the ledger (section 2.1). Defaults to the bill's amount and wallet. `FAILED` → that period is due again |
| `POST /bills/{id}/skip` | Skips the current period (`SKIPPED`) and moves to the next one |
| `DELETE /bills/{id}` | |

Due dates do not drift (31 Jan → 28 Feb → 31 Mar). A daily job sends `BILL_DUE_SOON` (`remindDaysBefore` days before)
and `BILL_OVERDUE`; a failed payment creates `BILL_PAYMENT_FAILED`.

```json
// POST /bills/{id}/pay → 202
{"id":"543950b0-…","dueDate":"2026-11-01","amount":800000,"walletId":"1e1a4d7a-…","paidOn":"2026-11-01",
 "status":"PENDING","transactionId":null,"failureReason":null}
// GET /bills/{id} afterwards: nextDueDate moved to the next period, payments[0].status = RECORDED with a transactionId
```

## 12. Investments

| Endpoint | Description |
|---|---|
| `POST /investments` `{name*, symbol?, type*, currency?, note?}` | `type`: `STOCK`, `FUND`, `GOLD`, `CRYPTO`, `BOND`, `REAL_ESTATE`, `OTHER`. `symbol` is upper-cased. The currency cannot change |
| `GET /investments`, `GET /investments/{id}` | Assets with their valuation and `trades` |
| `PATCH /investments/{id}` `{name?, symbol?, note?}`, `DELETE /investments/{id}` | Deleting only stops tracking; transactions already recorded in wallets stay |

- **Average cost**: a buy adds `quantity × price + fee`; a sell removes the average cost of the units sold, and the rest

  `PENDING → RECORDED`); refused → `FAILED` but the trade itself is kept (it happened at the broker). Without a wallet →
  `NONE`.

### 14.1 Push through FCM for the KMP app

1. Create a **Firebase** project and add the Android app (package name) and the iOS app (bundle id); for iOS upload an
   **APNs Authentication Key** (.p8) to Firebase (Project settings → Cloud Messaging). The backend enables FCM with
   `FCM_ENABLED=true` and the service-account key file (see `backend/README.md`, `docs/DEPLOYMENT.md`).
2. The app gets an **FCM registration token**: Android `FirebaseMessaging.getInstance().token`; iOS uses the Firebase iOS
   SDK (`Messaging.messaging().token`) after asking for notification permission and registering for APNs. In KMP, put
   both behind an `expect/actual`.
3. After sign-in: `POST /notifications/devices` `{"token":"<FCM token>","provider":"FCM","platform":"android"|"ios",
   "deviceName":"…"}` → `201 {token, provider:"FCM", …}`. Call it again whenever the SDK reports a new token
   (`onNewToken` / `messaging:didReceiveRegistrationToken`); calling it again with the same token is harmless. On
   sign-out: `DELETE /notifications/devices/{token}`.
4. FCM messages have a `notification` (`title`, `body` – displayed by the OS while the app is in the background) and
   `data` (strings): `notificationId`, `type`, `referenceType`, `referenceId` – use them to open the right screen when
   the user taps. Android messages use `channel_id = "default"` with high priority: **create the notification channel
   `default`** at app start-up (Android 8+); iOS gets `aps.sound = "default"`.
5. Tokens FCM reports as `UNREGISTERED` (app uninstalled) are removed by the backend. Quiet hours and disabled types
   apply as for every channel. While the app is open (foreground) FCM does not display anything itself: the app shows
   it or refreshes the list and `unread-count`.

## 15. Implementation tips for KMP

**Libraries**: Ktor Client (OkHttp on Android, Darwin on iOS) + `ContentNegotiation` with kotlinx.serialization,
kotlinx-coroutines, kotlinx-datetime, Koin, Compose Multiplatform (+ Navigation, Lifecycle ViewModel), Room KMP or
SQLDelight (cache), DataStore (settings), bignum (`com.ionspin.kotlin:bignum`) for money.

**JSON configuration**: `Json { ignoreUnknownKeys = true; explicitNulls = false; coerceInputValues = true }` – the
backend may add fields at any time. Enums: add a fallback value (`UNKNOWN`) or parse safely so that older app versions
do not break when the backend adds a new value.

**Money**: never `Double`. Write a `KSerializer<BigDecimal>` that reads the **raw content** of the JSON number
(`(decoder as JsonDecoder).decodeJsonElement().jsonPrimitive.content`) and writes it back with `JsonUnquotedLiteral` to
keep full precision. Display per currency (VND without decimals, dots as thousand separators with the `vi` locale).

**Authentication with Ktor**:

```kotlin
install(Auth) {
    bearer {
        loadTokens { tokenStore.read()?.let { BearerTokens(it.access, it.refresh) } }
        refreshTokens {
            // one refresh at a time (Ktor serialises them); the refresh token is single use
            val r = client.post("$base/api/v1/auth/refresh") {
                markAsRefreshTokenRequest(); setBody(RefreshRequest(oldTokens!!.refreshToken!!))
            }
            if (r.status == HttpStatusCode.OK) r.body<TokenPair>().also(tokenStore::save).let {
                BearerTokens(it.accessToken, it.refreshToken)
            } else { tokenStore.clear(); sessionEvents.emit(LoggedOut); null }
        }
        sendWithoutRequest { it.url.encodedPath.startsWith("/api/v1/auth/") }
    }
}
```

Store tokens in the Android Keystore (EncryptedSharedPreferences / encrypted DataStore) and the iOS Keychain through
`expect/actual`. When refresh returns `401` → clear the tokens and go to the sign-in screen.

**Errors**: map every non-2xx response to `ApiException(status, code, message, fieldErrors)` (the body may be empty for
`401`); the UI shows text based on `code` and puts `fieldErrors` under each input.

**Idempotency**: create a UUID when the user taps "Save" and keep it for every retry of that action (including after
an app restart if you have an offline queue).

**Asynchronous actions**: after `202`/`PENDING`, poll the object (every 1–2 seconds for up to ~10 seconds), then refresh
wallets and reports.

**Dates**: use `LocalDate` for every date field; "today" is in the `timeZone` of the user's profile.

**Suggested structure**: `core/network` (Ktor, auth, errors), `core/model` (Money, Currency), `core/storage`, `core/ui`;
`feature/{auth, wallet, transaction, budget, bill, saving, deposit, loan, investment, report, notification}` – matching
the backend modules and sections 4–14 of this document.

**Code generation from OpenAPI (optional)**: [`docs/api/openapi.json`](api/openapi.json) works with OpenAPI Generator
(`kotlin` + `library=multiplatform`) to generate DTOs. Still write the repository/use-case layers yourself, and replace
the money type (`number` → bignum `BigDecimal`). Re-export the file when the backend changes: run the backend, then
`curl -s localhost:8080/v3/api-docs | jq . > docs/api/openapi.json`.
